# 2026-09-03 — Jake's punch list

UI/feel fixes and one unreproduced bug, tracked here one item at a time.

**Process for each item, in order:**
1. Before touching any code, ask Jake a round of clarifying questions covering
   functionality, feel, and (for the bug) exact repro steps.
2. Make the smallest change that accomplishes the stated goal — not a
   redesign, not a bundled cleanup.
3. Update whatever doc/comment describes the changed behavior.
4. Build and install on Jake's phone; he verifies against his own tests.
5. Only then move to the next item.

## Items

- [x] **Trade text size.** The incoming-offer card's bot pitch line
      (`IncomingTradeCardView.swift`) was `.subheadline` with a
      `minimumScaleFactor(0.5)` floor - reported too small on Jake's
      iPhone. Bumped to `.headline` at full, unshrunk size; a new
      `MarqueeText` view scrolls the line (ticker-style, looping,
      65pt/sec) instead of shrinking or truncating it when it doesn't fit
      the row. Short lines sit still at full size. Verified on simulator
      (screenshots, confirmed actually animating) and on Jake's phone.
- [x] **Year of Plenty / Monopoly / Trade should use the old rounded-square
      cards, not hexes.** `ResourceChip.swift` (shared by `TradePopupView`,
      `DiscardPopupView`, and `DevCardPopupView`'s Monopoly/Year of Plenty
      picker) rendered painted-hex-art cards; changed to a flat
      resource-colored `RoundedRectangle` with the count printed below,
      matching `PlayerHUDView.resourceDot` (the human's own hand row on the
      main screen) exactly, per Jake's ask. Selection now shows as a gold
      stroke around the square. Verified on simulator (Trade, Monopoly
      screenshots) and installed on Jake's phone.
- [x] **Trade popup shouldn't close when a trade is proposed.** Investigated
      thoroughly (static trace of `apply`/`resolveHumanProposedTrade`/every
      banner, plus a real automated tap-through test) and could not
      reproduce it closing on propose - the actual complaint, per Jake's
      follow-up, was that the resolved-outcome banner ("No one accepted" /
      "X accepted!") only offered Close, so proposing again meant closing
      and reopening the popup. Added a "New Offer" button next to Close on
      that banner (`TradePopupView.swift`) that resets back to the builder
      without dismissing. Covered by
      `GameplayBoundaryFlowTests.testTradePopupStaysOpenAfterProposingToBots`
      (new accessibility identifiers on the give/want chips to support it)
      and verified on Jake's phone.
- [x] **Bug: something stops the game from advancing.** Root-caused and
      fixed via `superpowers:systematic-debugging`. `GameView.onAppear`
      pre-seeded `seenTradeOfferIDs` with every currently-*pending* bot
      trade offer (meant to stop a previously-shown offer from replaying),
      but that also permanently suppressed an offer that was pending and
      genuinely never yet shown to the human - closing/backgrounding the app
      while a bot's offer sat unanswered, then reopening, meant its card
      could never appear again (`handleTradeOffersChange`'s ingestion loop
      skips anything in `seenTradeOfferIDs`), while
      `GameViewModel.openIncomingOffer` (the bot loop's own gate, a live
      computed property with no such bookkeeping) kept seeing it as
      unanswered and parked the bot loop on it forever - a silent, permanent
      deadlock, matching "sometimes it happens if I close the game" exactly.
      Fixed by calling the real ingestion path (`handleTradeOffersChange()`)
      on appear instead of blindly marking everything seen. Reproduced with
      a real `app.terminate()` + relaunch (not just a same-process nav
      trick, which turned out to give a false negative - see the test's own
      doc comment) and covered by
      `GameplayBoundaryFlowTests.testIncomingOfferSurvivesAppRelaunch`,
      which fails against the old code and passes against the fix; all
      other `GameplayBoundaryFlowTests` still pass. The identical pattern
      also exists in `clearSeatInteractionState()` (the hot-seat handoff
      path) but was deliberately left unfixed - `human` resolves to the
      *outgoing* seat there, so the same fix would evaluate fulfillability
      against the wrong player without its own repro/verification first.
      Installed on Jake's phone for real-world confirmation.
